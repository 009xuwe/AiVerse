# 发布公告

正式版（`Android Release` workflow）发布时，会按版本号读取本目录下的 `<版本号>.md`，
内容直接出现在 GitHub Release 正文里，位置固定在「## APK 说明」标题下、包体表格上。

## 拼出来的样子

```markdown
## APK 说明

- 修复 …
- 改进 …

> [!NOTE]
> 升级说明

| 包名 | ABI | 适用设备 |
|---|---|---|
| AiVerse-arm64-v1.0.4.apk | arm64-v8a | 新手机（推荐） |
…
```

所以公告文件本身**从列表项开始写，不要再写 `##` 大标题**，否则会出现两个同级标题。

## 命名

| 发版输入的版本号 | 公告文件 |
|---|---|
| `1.0.4` | `1.0.4.md` |
| `1.0.4` + RC `1` | `1.0.4-rc1.md` |
| `2.4.1` | `2.4.1.md` |

文件名用**纯版本号，不加 `v`**。`v` 只出现在 git tag 上（`v1.0.4`）。

## 内容优先级

1. `docs-site/release-notes/<版本号>.md` 存在 → 用整份文件内容
2. 否则 workflow 的 `notes` 输入非空 → 用那一句（单行里换行写 `\n`，脚本会还原成真换行）
3. 都没有 → 正文只有 APK 说明表

文件存在时 `notes` 输入被忽略。

## 写法

普通 GitHub Markdown，以下几点可用：

- 列表项 `-`：每条改动一行
- 小标题 `### 修复` / `### 改进` / `### 新增`：需要分组时用
- `> [!NOTE]` / `[!IMPORTANT]` / `[!WARNING]` 告警卡片
- `#123` 会自动变成对应 issue 链接（GitHub 侧）

模板见 `_模板.md`，复制后改名为 `<版本号>.md` 即可。

## 容错

公告文件不存在、不可读、内容为空都不会让发版失败：脚本用 `[ -f ] && [ -r ]` 判断后
才 `cat`，且带 `|| true` 兜底，最差情况只是正文少了公告段，APK 照常发布。

## 与站点构建的关系

本目录放在 `docs-site/` 下是为了和官网文档归在一起管理，但 `.md` 不会被当作文档页面
发布出去；只有发版时 workflow 会读取它，对站点构建没有影响。
